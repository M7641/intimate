## The ideal: production you can summon with a string

The most underrated property a system can have is that its test environment is indistinguishable from production except for where it points. You bring up a container, you change a connection string, and the same code that runs against the real warehouse now runs against a local one. Nothing in the application layer knows or cares. The database connects to Redshift as easily as it connects to anything else, because the difference between "real" and "test" has been compressed down to a URL.

This is a more profound idea than it first appears. When the only thing separating your test bed from production is configuration, you have removed an entire category of bugs from existence — the bugs that live in the seam between "how we test" and "how we run." Mocks, fakes, in-memory stand-ins, and hand-rolled doubles all create that seam. Each one is a small fiction about how the real system behaves, and every fiction is a place where your tests can pass while reality fails. Containerised infrastructure — spinning up real services locally and addressing them exactly as you address production — collapses the fiction. You are not testing a model of the system. You are testing the system, smaller and cheaper and disposable, but the system nonetheless.

Adopting this for a Redshift and S3 workload is a clear step up. Instead of mocking the warehouse and the object store, you stand up containers that speak their protocols, point your connection objects at them, and let your real queries and real reads and writes flow through real wire formats. The test suite stops being a description of what you hope the code does and becomes evidence of what it actually does. That is the whole point of a test, and most test suites quietly fail to deliver it.

## The trap: "nearly the same" is a different thing entirely

There is a catch, and it is worth being precise about it, because it is the kind of flaw that hides inside a success.

The common move is to use PostgreSQL as the local stand-in for Redshift. The two are close relatives — Redshift began life as a fork of Postgres and still speaks a dialect that looks reassuringly familiar. So the container comes up, the string gets swapped, the tests go green, and everyone moves on. The fidelity feels total. It is not.

Redshift and Postgres are nearly the same, and nearly is the dangerous word. They diverge on column-store versus row-store execution, on distribution and sort keys, on data type coercion, on the functions each supports, on transaction and concurrency semantics, on how each plans and optimises a query, on what counts as valid SQL at the edges. A query that runs cleanly against Postgres can fail outright against Redshift, or — worse — succeed while returning different results or different performance characteristics. The space between "nearly the same" and "the same" is not empty. It is exactly the space where a test passes locally and fails in production.

And that specific failure mode is a small evil. Not because the bug is catastrophic in itself, but because of what it does to trust. A test that fails honestly is doing its job. A test that passes when it should fail is worse than no test at all, because it issues a guarantee it cannot keep. It tells the developer "this works" and lets the failure surface later, downstream, in production, where it is most expensive to find and most embarrassing to explain. You have paid the full cost of building a test suite and received, in exchange, false confidence. The Postgres-for-Redshift substitution buys you the *feeling* of perfect-fidelity testing while quietly reintroducing the very seam that containerised infrastructure was supposed to close — only now the seam is hidden, because the two systems are similar enough that you stop looking for it.

The principle that falls out of this is simple to state and worth holding firmly: **test against the real technology, not its near-relative.** If you run Redshift in production, your test bed should run Redshift, or something the vendor certifies as behaviourally identical — not a cousin that happens to share a wire protocol. The value of the URL-swap architecture is only as good as the fidelity of the thing on the other end of the URL. A perfect mechanism pointed at an imperfect replica is still imperfect; it has just moved the imperfection somewhere harder to see.

## The deeper point: testability as a selection criterion

Once you take fidelity seriously, it stops being a detail of how you test and becomes a property you should demand of the technologies you adopt in the first place.

A technology that can be run locally, addressed identically to production, and trusted to behave identically is a technology you can build on with confidence. One that cannot — one that exists only as a remote, proprietary, un-reproducible service — forces you back into the world of mocks and fictions and seams, however good your intentions. So "does this have a perfect testing story?" deserves a seat alongside performance, cost, and features when you choose what to build with. It is not a secondary concern. It is the difference between a system you can reason about and one you can only hope about.

This reframes the real problem with low-code and no-code platforms. The usual critiques — vendor lock-in, ceilings on customisation, performance — are real but somewhat beside the point. The deeper issue is that these platforms typically offer no way to stand up a faithful copy of your production environment and exercise it the way real code can be exercised. There is no container to bring up, no string to swap, no local instance that behaves exactly as the hosted one does. The logic lives inside a proprietary runtime you cannot fully reproduce, so the seam between test and production isn't just present — it's unavoidable and unfixable. You cannot close it, because the platform never gave you the parts.

That is the flaw worth naming. The strength of code plus real, containerised infrastructure is not that it is more powerful in the abstract; it is that it can be tested with perfect fidelity, end to end, against the genuine article. The weakness of low-code is not that it is simple; it is that it forecloses that possibility. It asks you to trust that what works in its environment will work in production, and it gives you no honest way to check. After everything above, that should read as the most serious charge of all — because a system you cannot faithfully test is a system you are running, in the end, on faith.

## Testing in the world of AI

This has always been a point of concern since the dawn of software, with the concept described by the phrase: "It works on my machine". With the addition of AI, my argument is that this gets worse, not better. A test environment that an agent can interact with, but is different to the real thing, creates space for AI to introduce huge numbers of bugs that then require significant resources to resolve when the push to production fails. It's true that a lot of this resource can be AI itself, but it's still a waste of either human time or AI resources. 

This has increased the value of having a perfect fidelity test environment. This leads to one of my conclusions: we should not use Snowflake or Redshift unless we absolutely have to. When we do, we should be prepared to invest the resources to have a perfect testing environment. This would essentially double the cost, as we would want to run everything twice. 

It's also a slowdown to development, as you can't spin up these services in a local container; you need to deploy them to the cloud service to test and then run. Not good for DX.
