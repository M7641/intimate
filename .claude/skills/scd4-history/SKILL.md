# SCD Type 4 — history-table dimensions

Track the full history of a dimension table without bloating the table everyone
queries. **Type 4 splits storage by access pattern:** the main dimension holds
exactly one current row per business key (fast joins, no version filtering), and a
sibling `<table>_history` holds every version, effective-dated, for time-travel
and audit.

```
dim_customer              -- current state, 1 row / customer_id   (what dashboards join to)
dim_customer_history      -- every version, valid_from..valid_to  (audit, point-in-time)
```

## When Type 4 is the right call

| You want… | Use |
|---|---|
| Current state queried constantly, history rarely | **Type 4** (this skill) — keep the hot table lean |
| Every query to be time-aware; one table with a `current` flag | Type 2 (not this skill) |
| Just overwrite, no history at all | Type 1 |
| A handful of fast-churning attributes blowing up a Type 2 | Type 4 *mini-dimension* (different shape — ask) |

The deciding question: **do most consumers want "now", with history as the
exception?** If yes, Type 4 stops them paying the version-filtering tax on every
join. If every consumer is time-aware, Type 2 is simpler. Don't reach for Type 4
by reflex — name the access pattern first.

## The two tables

**Current** (`dim_customer`) — the table you already have, or a fresh one: one row
per business key, the live attribute values. Consumers join to it directly.

**History** (`dim_customer_history`) — generated by this skill. Holds **every**
version, current included (`is_current = TRUE` marks the live one), with:

- `scd_id` — surrogate version key (`IDENTITY`)
- the business key(s) + tracked + static columns
- `row_hash` — MD5 over the tracked columns, used for change detection
- `valid_from` / `valid_to` — the effective window (`valid_to = '9999-12-31'` is open)
- `is_current` — convenience flag so you needn't compare timestamps to find "now"

Keeping the current version *inside* history (not only the superseded rows) makes
history self-contained: a single point-in-time query never has to UNION the live
table. The cost is one duplicated row per key — cheap, and worth it.

## Generate the SQL

Don't hand-write the load — the change-detection hash and the column lists are
fiddly and easy to get subtly wrong. Describe the table in a JSON config and run
the generator.

1. **Write a config** (copy [assets/example_config.json](assets/example_config.json)).
   The three column groups carry the whole design:
   - `business_key` — the natural identity. Never versioned. (one or more columns)
   - `tracked_columns` — a change in **any** of these opens a new version.
   - `static_columns` — carried onto every version, but a change here does **not**
     trigger a version. (See the static-column gotcha below.)

2. **Run it:**
   ```bash
   python scripts/generate_scd4.py --config table.json --out-dir ./sql
   # add --full-snapshot if staging is a full reload (handles vanished keys / deletes)
   ```
   It writes `<table>_history.ddl.sql` (run once) and `scd4_load_<table>.sql` (run
   each batch).

3. **Wire the load** into your orchestrator (dbt model/op, Airflow task, plain
   `psql`). The load reads from a staging table `stg_<table>` you populate with the
   incoming snapshot. Substitute the one `{load_ts}` placeholder — see below.

## How the load works (read before running it)

Four steps, one transaction. Understanding them is what lets you debug a bad load:

1. **Detect** — left-join staging to the current dimension, flag rows that are
   new (no current match) or changed (tracked-column hash differs) into a temp table.
2. **Close** — for changed keys, stamp the open history row: `valid_to = {load_ts}`,
   `is_current = FALSE`.
3. **Insert** — write the new version into history, open-ended and current.
4. **Upsert** — replace the current dimension row (DELETE the changed keys, INSERT
   the new state — Redshift's idiomatic upsert, since old PG forks lack `MERGE`).

`--full-snapshot` adds a step 5 that closes out keys which disappeared from staging
(hard deletes). Use it only when staging is a *complete* reload; with deltas it
would wrongly retire everything not in this batch.

## The two things that bite people

**`{load_ts}` must be a single instant for the whole batch.** Substitute one
timestamp captured at the start of the run (dbt's `run_started_at`, Airflow's
logical date), not `GETDATE()` per statement. If the close and the insert use
different clocks, the old row's `valid_to` won't exactly meet the new row's
`valid_from`, and point-in-time queries get gaps or overlaps at the seam.

**Static columns only refresh when a tracked column also changes.** Because change
detection hashes *tracked* columns only, a row whose sole change is in a static
column is invisible to the load — neither history nor the current table updates. If
a column must always reflect the latest value, make it `tracked`, not `static`.
`static` is for genuinely immutable facts (e.g. `signup_date`).

## Querying it

```sql
-- current state — just join the lean table, no filter
SELECT * FROM analytics.dim_customer;

-- point-in-time: what every customer looked like on a date
SELECT * FROM analytics.dim_customer_history
WHERE '2025-03-01' >= valid_from AND '2025-03-01' < valid_to;

-- full history of one key
SELECT * FROM analytics.dim_customer_history
WHERE customer_id = 42 ORDER BY valid_from;
```

Note the half-open interval `[valid_from, valid_to)` — `>=` on the low end, `<` on
the high end. This is what makes adjacent versions tile a timeline with no gap and
no double-count at the boundary instant.

## Guardrails

- **Never** populate `{load_ts}` with a per-statement clock — one instant per batch.
- **Never** run `--full-snapshot` against a delta feed — it will retire live keys.
- **Always** load via the generated transaction as a whole; a partial load leaves
  history and the current table disagreeing about what "now" is.
- If the user's real need is "every query is time-aware," stop and recommend Type 2
  instead — Type 4's lean current table buys nothing there.
