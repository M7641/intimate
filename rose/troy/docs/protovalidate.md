# protovalidate — value constraints inside the proto

> Status: **design / production-target.** Not wired into the runnable `make demo`
> build, because this machine has no `buf`/`protoc` and the Rust runtime is not
> ready (see [Runtime asymmetry](#runtime-asymmetry)). The plain
> `registry/proto/contracts/customer/v1/customer.proto` keeps the rules as
> comments + a hand-written Rust `validate()`. This document is what that file
> *becomes* in production.

## The idea

Today the Customer value rules live **twice**: as comments in the `.proto`, and
re-implemented by hand in `rust/src/main.rs::validate()`. `buf.validate`
(the [protovalidate](https://github.com/bufbuild/protovalidate) project) removes
that duplication by moving the rules **into the proto as declarative
annotations**, enforced **at runtime** by a shared library.

The mental shift is the same one the ingestion boundary already makes with JSON
Schema: **a constraint is data, not code.** You stop writing `validate()` and
start calling `protovalidate.validate(msg)` — the library reads the rules off
the message descriptor.

```
  prototype (now)                     production (this doc)
  ───────────────                     ─────────────────────
  rule in proto comment        ─►     rule in proto annotation  (single source)
  + Rust validate() by hand    ─►     protovalidate.validate(msg) reads it
  + pydantic models.py dup     ─►     protovalidate.validate(msg) reads it
```

## The annotated contract

This is what `customer.proto` looks like with full `buf.validate` annotations:

```proto
syntax = "proto3";
package contracts.customer.v1;

import "buf/validate/validate.proto";   // resolved from the BSR, not vendored

message Customer {
  // ── message-level rule: a cross-field invariant, expressed in CEL ──
  option (buf.validate.message).cel = {
    id:         "customer.enterprise_revenue"
    message:    "enterprise customers must report a positive annual_revenue"
    expression: "this.tier != 4 || this.annual_revenue > 0"
  };

  // ── standard constraints, one per scalar type ──
  string customer_id = 1 [
    (buf.validate.field).string.pattern = "^cust_[a-z0-9]+$",
    (buf.validate.field).string.max_len = 64
  ];

  string email = 2 [
    (buf.validate.field).string.email   = true,
    (buf.validate.field).string.max_len = 254
  ];

  Tier tier = 3 [
    (buf.validate.field).enum.defined_only = true,   // reject values outside the enum
    (buf.validate.field).enum.not_in       = [0]      // reject TIER_UNSPECIFIED
  ];

  double annual_revenue = 4 [
    (buf.validate.field).double.gte = 0,
    (buf.validate.field).double.lte = 1e12
  ];
}

enum Tier {
  TIER_UNSPECIFIED  = 0;
  TIER_FREE         = 1;
  TIER_STARTER      = 2;
  TIER_PROFESSIONAL = 3;
  TIER_ENTERPRISE   = 4;
}
```

Note `enum.not_in = [0]`: it formalises in the contract the rule the prototype
hard-codes (`tier == Unspecified → error`). proto3's mandatory zero value — the
thing that makes adding new tiers backward-compatible — becomes explicitly
rejected at the edge, with zero application logic.

## Three levels of rule power

From simplest to most powerful:

1. **Standard constraints** — a large built-in library per scalar type:
   `string.pattern`, `string.email`, `string.uuid`, `double.gte/lte`,
   `int32.gt`, `enum.defined_only`, `repeated.min_items`, `timestamp.lt_now`, …
   The direct equivalent of JSON Schema keywords.
2. **Field-level CEL** — for anything no standard rule covers:
   `(buf.validate.field).cel = { expression: "this.startsWith('cust_')" }`.
3. **Message-level CEL** — **cross-field invariants** (`max > min`,
   `enterprise ⇒ revenue > 0`). This is the case where protovalidate is less
   natural than CUE was: it *can* express it, but via CEL, not via the type
   system.

## The dependency (the "buf extension" mechanics)

`buf.validate` is not part of Protobuf — it is a module distributed on the Buf
Schema Registry. You declare it in `buf.yaml`:

```yaml
version: v2
deps:
  - buf.build/bufbuild/protovalidate   # provides buf/validate/validate.proto
modules:
  - path: .
```

Then `buf dep update` writes a `buf.lock` pinning the version. The
`import "buf/validate/validate.proto"` resolves from the BSR — **nothing is
vendored**. That is what "the buf ecosystem" means: proto options packaged and
versioned like dependencies.

`buf generate` is unchanged — the standard prost/betterproto plugins emit the
message types, and the `buf.validate` options ride along in the generated
descriptors for the runtime library to read.

## Runtime enforcement

### Python — solid, official

The hand-written validation disappears entirely:

```python
import protovalidate
from troy.gen.contracts.customer.v1 import Customer   # generated by buf

msg = Customer(customer_id="CUST-ABC", email="nope", tier=0, annual_revenue=-42)
try:
    protovalidate.validate(msg)
except protovalidate.ValidationError as e:
    for v in e.violations:
        print(v.field_path, "→", v.message)
    # customer_id    → value does not match regex ^cust_[a-z0-9]+$
    # email          → value must be a valid email address
    # tier           → value must not be in [0]
    # annual_revenue → value must be greater than or equal to 0
```

### Runtime asymmetry

This is the deciding constraint for Troy, and it must be known before adopting.
protovalidate's **official** runtimes are Go, Java, Python, C++, and TypeScript.
**Rust is not among them.** Troy's internal boundary is Rust ↔ Python, so:

| End | Option | Maturity |
|-----|--------|----------|
| Python | `protovalidate` (PyPI, official) | ✅ production-ready |
| Rust | `protovalidate-rs` (community) | ⚠️ younger — verify before relying |
| Rust | `prost-validate` (PGV-style, separate annotations) | ⚠️ **not** `buf.validate`-compatible |
| Rust | keep hand-written `validate()` / `garde` | ✅ works, but manual |

The pragmatic stance for Troy: **annotations in the proto are the single source
of truth; Python enforces them with `protovalidate`; Rust keeps the mirrored
`validate()` (or `garde`) until `protovalidate-rs` matures.** The source of
truth stays single — only the Rust *enforcement* remains manual.

> This is the CUE lesson replayed one level down: the value of "declare once,
> enforce everywhere" depends entirely on a runtime existing in **every** target
> language. Go↔Python: perfect symmetry. Rust↔Python: the bridge is shaky on the
> Rust side. Runtime availability per language is *the* deciding factor — same as
> why CUE (Go-only) was rejected.

## What it removes from the prototype

| Aspect | Prototype (now) | With `buf.validate` |
|--------|-----------------|---------------------|
| Where rules live | proto comments + Rust `validate()` | declarative proto annotations (one source) |
| Python | duplicated pydantic `models.py` | `protovalidate.validate(msg)`, zero dup |
| Rust | mirrored `validate()` | ideally `protovalidate-rs`; else mirrored (unchanged) |
| Cross-field rules | absent | message-level CEL (`enterprise ⇒ revenue`) |
| Dependency | none | `buf.build/bufbuild/protovalidate` via `buf dep` |

## Making it runnable later

When `buf` is available (`brew install bufbuild/buf/buf`):

```bash
cd registry/proto
buf dep update                 # resolve + lock buf.build/bufbuild/protovalidate
buf lint && buf generate       # emit Rust + Python types with the validate options
# Python:
uv run --with protovalidate python -c "import protovalidate; ..."
```

Without `buf`, a Python-only path also works via `grpcio-tools` (which bundles
`protoc`) plus the `protovalidate` package — but it requires the
`buf/validate/*.proto` sources on the include path, so `buf dep update` (or
vendoring those protos) is still the simplest route.
